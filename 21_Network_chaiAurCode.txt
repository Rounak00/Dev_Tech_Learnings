 vid 22 > MTU MSS PMTUD
  
Maximum Transmission Unit (MTU) -> Largest IP Packet without fragmentation. includes IPHeader + TCP/UDP Header + Payload. Ethernet eader not part of it. different links can have different MTU. Excedding MTU can cause fragmentations or packet drops.
MTU is there so we can avoid fragmentation, Keeping packets within the MTU avoids fragmentation, which can introduce additional headers, processing overhead, and packet-loss/retransmission inefficiency.

Maximum Segment Size (MSS) -> TCP Only, Maximum TCP Payload in a single segment without TCP Header
 - MSS = MTU - IP HEader - TCP HEader/
 - Standard Ethernet MSS = 1460 bytes (No one remeber this shit)
 - Advertised during TCP 3-Way handshake, carried in TCP MSS option, helps to avoid fragmentation

 * MSS helps to make segments based on the mss and total data size

 
 Path Maximum Transmission Unit Discovery (PMTUD) -> 
   - Each router have an MTU through which segments hopps and go to the destination
   - Mechanism to discover PMTU, prevent fragmentation
   - Sender starts with larger packets,and router dropped oversized packets & send ICMP " Fragmentation needed" then sender reduce packet size and try again -> this way continue until packet passes successfully


also during PMTU we set DF = 1  [means packet cant be fragment] so lower MTU router after receive a larger packet it will not fragment it , instead it drops and return ICMP "Fragmentation Needed"

How much reaciver can handle and my sender can send?

DNS MX Record

• Used by SMTP servers during email delivery
• Lower preference value = Higher priority
• Multiple MX records can exist for redundancy and failover
• MX records contain hostnames, not IP addresses
• SMTP servers perform A or AAAA lookups on the MX hostname
  before connecting
• If the highest-priority mail server is unavailable,
  the next MX record is tried
• MX records do not store emails,
  they only show where emails should be delivered
• Multiple MX records with the same preference
  can be used for load balancing

Now why Quic uses UDP under hood not make it a direct TCP/UDP like one ?

Protocol ossification means the Internet infrastructure has become so optimized for TCP and UDP that introducing a completely new transport protocol is difficult.
 -Routers, firewalls, and NATs expect TCP or UDP.
 -A new protocol may be blocked or handled incorrectly.
 -QUIC solves this by running inside UDP.
 -So, network devices simply see normal UDP traffic and forward it.
 -QUIC can then be improved/updated by applications without waiting for OS vendors, router manufacturers, or network upgrades.

video 43 > TLS certification

TLS Certificate
- Digital certificate used to establish the identity of a server
- Binds a domain name to server's public key
- Issued and digitally signed by a Certificate Authority (CA)
- Contains information such as domain, public key, issuer, validity period, and CA signature
- Used during the TLS handshake to authenticate the server and establish a secure connection

> Generating a TLS certificate:
A. Server who wants the certificate (e.g. ssw.in)
- Create Public/Private key pairs
- Create Certificate Signing Request (CSR)
- Submit CSR to CA
	The CSR contains the server's public key
	The private key stays with the server
- Deliver signed certificate and install it on server

B. Certificate Authority (CA) e.g. Let's Encrypt
- Construct tbsCertificate (To Be Signed Certificate)
	Adds Subject Public Key, Issuer Name, Validity, Extensions, etc.
- Serializes and encode the certificate using
	ASN.1 (Abstract Syntax Notation One) and
	DER (Distinguished Encoding Rules)
- Sign with CA's Private Key
	Right side flow: To Be signed Certificate -> ENCODE (ASN.1, DER) -> DER-encoded TBSCertificate bytes -> Sign DER-encoded TBSCertificate using CA's Private Key
- Final X.509 Certificate (tbsCertificate + Signature Algo. + Signature)

C. Final Assembly
- Assemble Final X.509 Certificate = tbsCertificate bytes + signatureAlgorithm + signature

> Verifying TLS certificate from the image:
Flow:
- User visits ssw.com in the browser
- TLS handshake begins, Server sends its certificate chain
- Server returns the certificate (leaf certificate (own) + required intermediate CA certificates)
- Parse the certificate into:tbsCertificate bytes, signatureAlgorithm, Actual signatureValue (signed using issuer's (CA) Private Key)
- Verify signature using issuer's (CA) Public Key
	Note: The signature was created using the issuer's private key, the issuer public key is used to verify it
- If the signature is verified, means it was indeed signed by the issuer (CA)
- Repeat certificate verification up the chain until a trusted root CA is reached.
Other certificate checks:SAN / hostname Validity period Other constraints 

Chain of trust => verify till Root certificate (self signed of cert), browser and os knows about this certificate

Browser → Server: TLS in simple terms
1. Browser connects to https://ssw.com 
2. Server sends its TLS certificate → certificate contains the server's public key.
3. Browser verifies the certificate:
Is it for ssw.com?
Is it valid?
Is it signed by a trusted CA?
4. If valid, the browser now trusts the server's public key.
5. Browser and server perform the TLS handshake and establish a shared session key.
6. After that, actual HTTP data is encrypted using the session key (symmetric encryption).







video 44 > Maths behind Diffie hellman
Diffie-Hellman (Whitfield Diffie and Martin Hellman)
- Key exchange protocol Uses publicly known parameters: prime p and generator g
- Based on the Discrete Logarithm Problem
- ECDHE is the modern elliptic-curve variant widely used in TLS
- Diffie-Hellman is key exchange algo, not message encryption

Basic Diffie-Hellman example to get a symmetric key.
We want a shared secret, but we are on an untrusted network. We can only send public values.
1. Public parameters (everyone knows):
	Prime p = 23	
	Generator g = 5
2. Private secrets (never shared):
	Alice picks private a = 6
	Bob picks private b = 15
3. They calculate their Public Keys to exchange:
		Alice: A = g^a mod p = 5^6 mod 23 = 15625 mod 23 = 8
		Bob: B = g^b mod p = 5^15 mod 23 = 19
	They exchange A=8 and B=19 over the open network. An attacker sees 8 and 19, but can't get a or b because of the Discrete Logarithm Problem.
4. They calculate the SAME shared secret:
	Alice computes: Secret = B^a mod p = 19^6 mod 23 = 2
	Bob computes: Secret = A^b mod p = 8^15 mod 23 = 2
	Shared Secret = 2
This 2 is now the symmetric key. 
In real TLS, this number is much bigger (2048-bit) and then passed through a Key Derivation Function (KDF) to create the actual AES session key.
This is why DH is a key exchange algo, not encryption. It just lets both sides agree on the same symmetric key securely.

NAT (Network Address Translation)
• IPv4 addresses are limited to 4 billion
• IPv4 address can be private (192.168.x.x / 10.x.x.x) or public (8.8.8.8)
• NAT is primarily used to allow multiple private devices

A - 10.0.0.1 -> Router (10.0.0.10) -> Public IP 2.3.4.5
B - 10.0.0.2 -> Router (10.0.0.10) -> Public IP 2.3.4.5

D - 10.0.0.5 -> Router (10.0.0.10) -> Public IP 2.3.4.5

1. Version: Tells the receiver which version of IP is being used.
	IPv4 → 4
	IPv6 → 6
	
2. IHL — Internet Header Length
Tells the size of the IPv4 header.
IHL = 5 → minimum header size = 20 bytes
IPv4 can have optional fields.

3. DSCP — Differentiated Services Code Point
Used for traffic classification/prioritization. Routers can use DSCP to decide how traffic should be handled.

4. ECN — Explicit Congestion Notification
Used to indicate network congestion without necessarily dropping packets.
Instead of: Congestion → Drop packet
ECN can allow devices to communicate: "Network is becoming congested"
The sender can then reduce its sending rate.

5.Total Length: Specifies the total size of the IPv4 packet. Includes: Header + Data
Maximum IPv4 packet size: 65,535 bytes

6. Identification : Mainly related to fragmentation.
If a large IP packet needs to be broken into smaller pieces:
Original packet
       ↓
 ┌─────┬─────┬─────┐
 │ F1  │ F2  │ F3  │
 └─────┴─────┴─────┘
All fragments have the same Identification value, allowing the destination to know: "These fragments belong to the same original packet."

7. Flags: Controls fragmentation.
Important flags:
	> DF — Don't Fragment = 1, means: Don't fragment this packet.
		If the packet is too large for the next network and fragmentation isn't allowed, it can be dropped.
	> MF — More Fragments = 1, means:  more fragments are coming. The last fragment has: MF = 0
	
8. Fragment Offset: Tells the receiver where this fragment belongs in the original packet.
Example: Original: [A B C D E F G H]
After fragmentation: Fragment 1 → [A B C], Fragment 2 → [D E F], Fragment 3 → [G H]
The fragment offset helps the receiver put them back in the correct order.

9. TTL — Time To Live :  Prevents packets from circulating forever.
Example: TTL = 64
Router 1 → TTL = 63
Router 2 → TTL = 62
Router 3 → TTL = 61
...

Each router decreases TTL by 1.
When TTL reaches 0, the packet is discarded.
This protects the network from routing loops:
Router A → Router B
    ↑          ↓
    └──────────┘
Without TTL, a packet could potentially loop indefinitely.

10. Protocol: Tells IP which upper-layer protocol should receive the payload.
Common values: TCP   → 6, UDP   → 17, ICMP  → 1
For example:
IPv4 Packet
     │
     ├── Protocol = 6
     ↓
    TCP
So the receiver knows how to interpret the data.	

11. Header Checksum: Used to detect errors in the IPv4 header.
	Important: It checks the header, not the payload.
	Routers also recalculate it because fields such as TTL change at every hop.
Router
  ↓
TTL changes
  ↓
Header checksum recalculated

12. Source Address: The IP address of the sender.
13. Destination Address: The IP address of the intended receiver.
14. Data / Payload: Actual data being carried by the IP packet.
For example:
IPv4
 │
